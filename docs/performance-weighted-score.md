# 单位履约加权分

## 目的与页面位置

“单位履约加权分”是项目级履约明细与清标测算之间的正式业务边界。页面顺序为：查询筛选、季度履约评分一览、履约数据明细、单位履约加权分。模块不是独立全局台账，所有查询、保存、失效和读取都以 `projectId` 为第一作用域。

## 数据来源与行身份

每一行的业务身份是：

```text
projectId + candidateId + projectType
```

候选单位只能来自当前 `ProjectCandidate`；项目类型只能来自当前项目 `ProjectRuleProjectType`。同一候选单位可按幕墙、装修、总包、实验室等不同项目类型保存多行，不允许同一候选单位与同一项目类型重复行。

页面加载时即按当前项目履约明细中的 `candidateId + projectType` 去重生成派生行，不需要先点击“新增一行”或“从履约明细同步”。“从履约明细同步”保留为显式修复能力：它只补充尚未配置的组合，不删除人工已配置行，也不跨项目读取同名公司。

未关联 `ProjectCandidate` 的 legacy 履约记录不会通过 `companyName` 猜测归属，也不会进入当前加权分或清标；read model 会返回未关联记录数量供页面提示。

## 动态季度列

起始季度与结束季度定义一个连续、包含两端的季度范围。季度列由 Domain 的季度序列函数动态生成，跨年时自动从 Q4 进入下一年 Q1；数据库没有为某个年份或季度创建物理列。“新增季度列”把结束季度顺延一个季度。

每个季度单元格读取：

```text
projectId
+ candidateId
+ projectType
+ year
+ quarter
```

匹配到多条 `CompanyPerformance` 明细时，先对该季度全部明细分数做等权平均，得到季度平均分；没有数据时为 `null`，UI 显示 `—`，不得转换为 0。为支持真实多明细，旧的同单位、同类型、同季度唯一约束已改为普通查询索引。

分类分级等级同样从该单位/项目类型的履约明细派生。全部明细等级一致时自动回填；存在多个不同等级时不随机选择任意一条，而是返回冲突等级集合并在页面提示数据一致性问题。

## 加权规则

两种正式方法都先在用户选择的起止季度范围内形成季度平均时间序列，按 `year ASC + quarter ASC` 排序，取最新最多 12 个有效季度。缺失季度不作为 0 分，也不占用权重序号。

### 等权平均

内部值：`EQUAL_RECENT_12`。

```text
A = ΣAi / n
```

### 时间线性加权

内部值：`LINEAR_RECENCY_RECENT_12`。对参与计算的有效季度按最旧到最新动态赋权 `1, 2, …, n`：

```text
A = Σ(i × Ai) / Σi
i = 1...n, oldest → newest
n ≤ 12
```

完整 12 季度时权重和为 78；最新季度权重为 `12/78`。少于 12 个有效季度或中间存在缺失季度时，按实际有效季度数量从 1 重新编号。不存在硬编码的小数权重数组。

统一计算流程为：

1. 在用户选择的起止季度范围内取该行有数据的季度；
2. 按季度从旧到新排序；
3. 最多取最近 12 个有数据季度；
4. 根据所选方法做等权或时间线性加权；
5. 少于 12 个季度时按实际有数据季度计算；没有任何数据时为 `null`。

季度聚合复用 `src/domain/performance/company-performance.ts`，两种加权方法统一由 `calculateWeightedPerformanceScore()` 分派。React、Server Action、Repository 和清标页面均不复制公式，Domain 和 canonical persistence 不做展示舍入。

## 保存、current 与 stale

`Project.performanceInputRevision` 表示加权分输入版本。履约明细新增、修改、删除，候选单位新增或删除，以及项目类型实际变化会递增该 revision。

保存时，应用服务按数据库中的当前明细重新计算，客户端不能提交可信分数。Repository 在事务内再次核对 revision、候选单位、项目类型和重复行，然后覆盖保存：

- `PerformanceWeightedSnapshot`：项目、输入 revision、起止季度、加权方式、保存时间；
- `PerformanceWeightedScore`：候选单位、项目类型、分类分级、加权平均、参与季度数。

状态定义：

- `not_saved`：尚无正式快照；
- `current`：快照的输入 revision、起止季度和加权方式均与当前页面方案一致；
- `stale`：任一项不一致，包括用户切换了尚未保存的加权方式。

履约明细变更不会删除旧快照，而是把它自然标记为 stale，便于页面提示与审计。页面上的季度分和加权平均属于实时派生 read model，会在新增、编辑、删除后的 `router.refresh` 中立即重新计算；保存新快照会递增清标/定标输入 revision，使旧测算结果失效。

## 清标共源

清标只读取当前项目、当前 revision 的 `PerformanceWeightedSnapshot`。快照不存在、已经 stale、候选单位缺少当前任一项目类型行，或某行没有加权平均分时，该候选单位履约数据视为不完整，禁止继续把旧分数当作 current。

多个项目类型时，先按所选方法分别得到各项目类型的加权平均，再沿用既有规则对专业平均值等权平均。专业之间的业务权重仍未给出，继续标记为待业务确认；它与本次“同一专业内的季度加权方式”是两个独立层次。

## 导出与显示

CSV、正式 Excel 和报告均明确输出当前加权方式。CSV 按当前配置行和动态季度列导出，缺失值保持空单元格。分数只在 UI/导出边界格式化；数据库、DTO 与 Domain 使用规范十进制字符串，避免浮点数精度变化。

## 不变量

- 所有读写必须包含 `projectId`；A 项目的保存和失效不得影响 B 项目。
- 项目类型修改不删除历史履约明细；历史类型仍可在明细中查看，但当前加权同步与清标只使用当前项目类型。
- 季度概览的 `recordCount` 仍表示完整季度数据库状态，不受加权模块的临时类型筛选影响。
- 本模块不修改 Qingbiao、Dingbiao、Analysis 的核心公式。
